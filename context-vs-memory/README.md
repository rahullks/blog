# context-vs-memory

Companion code for the post *"Measuring the crossover from context engineering to agent memory."*

A small, self-contained experiment comparing three ways an agent can answer questions about
something said earlier in a long conversation. The conversation carries 40 facts scattered
through unrelated filler, and each approach gets a fixed 120-token budget.

1. **Recency truncation**: naive baseline, keep only the most recent turns.
2. **Context packing**: a real context-engineering technique. Score the raw conversation
   history against the current query (TF-IDF relevance) and pack the highest-scoring turns into
   a fixed token budget.
3. **Memory retrieval**: extract facts into a small external store as the conversation happens,
   then score only that store against the query.

We measure recall (did the right fact make it into the assembled context?) and a compute proxy
(how many turns had to be scored) as the conversation grows from 80 to 800 turns.

## How relevance is scored

Relevance scoring uses TF-IDF cosine similarity (scikit-learn) as a deterministic stand-in for
embedding-based retrieval, so the core comparison runs offline and returns the same numbers every
time. That's a deliberate simplification: it isolates the retrieval and scaling question from
model-specific behavior. See the caveats at the bottom of the notebook for what it hides.

For real semantic scoring, `src/local_backend.py` swaps in a local embedding model. See "Two rungs
of relevance scoring" below.

## Two rungs of relevance scoring

Every approach in `sim.py` takes a `scorer` argument with one contract:
`rank_by_relevance(query, candidates) -> [(Turn, score)]`, sorted descending. Two implementations
ship here, and nothing else changes between them.

| rung | scorer | setup | matches on |
|---|---|---|---|
| 1 | `sim.rank_by_relevance` (default) | already installed | literal word overlap |
| 2 | `local_backend.LocalEmbeddingScorer` | `pip install fastembed` | meaning |

### Rung 2: local embeddings

```bash
pip install fastembed
python3 src/eval_lexical_vs_semantic.py
```

Uses `BAAI/bge-small-en-v1.5` through [fastembed](https://github.com/qdrant/fastembed), which runs
ONNX on CPU. The model (~130MB) downloads on first use and is cached in `~/.cache/fastembed`, so
later runs need no network.

```python
from local_backend import LocalEmbeddingScorer
import sim

scorer = LocalEmbeddingScorer()
text, tokens, scored = sim.approach_context_packing(
    conversation, query, token_budget=120,
    max_scorable_history=300, scorer=scorer.rank_by_relevance)
```

**Does it change the result?** Mostly no, and the reason is worth knowing. `eval_lexical_vs_semantic.py`
runs the recall measurement against both the original `QUERIES` and `PARAPHRASED_QUERIES` (the same
40 facts asked using none of the fact's own words):

| scorer | query set | turns | context packing | memory retrieval |
|---|---|---:|---:|---:|
| TF-IDF | original | 120 / 300 | 1.00 | 1.00 |
| TF-IDF | paraphrased | 120 | 0.23 | 0.35 |
| TF-IDF | paraphrased | 300 | 0.25 | 0.35 |
| bge-small-en-v1.5 | original | 120 / 300 | 1.00 | 1.00 |
| bge-small-en-v1.5 | paraphrased | 120 | 0.53 | 0.85 |
| bge-small-en-v1.5 | paraphrased | 300 | 0.45 | 0.85 |

On the original queries the two scorers are indistinguishable, because those queries reuse the
words of the fact they ask about, which hands a lexical matcher the answer. The difference only
appears once the query is phrased differently from the fact, and then it is large: memory
retrieval goes from 0.35 to 0.85, context packing from ~0.24 to ~0.49.

Semantic scoring helps memory retrieval most, because that lane is pure ranking over a bounded
store, which is exactly what a better scorer improves. It does not rescue context packing at
length, since no amount of ranking quality reaches a turn the scorer never saw.

This is not an artifact of picking one small model. `src/eval_across_models.py` runs the same
measurement across bge-small, bge-base, arctic-embed-s and MiniLM-L6-v2. Every one ties word
matching on the original queries and beats it clearly on the reworded ones, and the spread between
models (0.85 to 0.95 on memory retrieval) is much smaller than the gap between word matching and
meaning (0.35 to 0.85).

## What the result looks like

40 facts, 40 queries, a 120-token budget, and a 300-turn scoring cap:

| conversation_length | approach            | recall | avg_turns_scored |
|---:|---|---:|---:|
| 80  | context_packing     | 1.000 | 80  |
| 80  | memory_retrieval    | 1.000 | 40  |
| 80  | recency_truncation  | 0.125 | 0   |
| 240 | context_packing     | 1.000 | 240 |
| 240 | memory_retrieval    | 1.000 | 40  |
| 240 | recency_truncation  | 0.050 | 0   |
| 480 | context_packing     | 0.625 | 300 |
| 480 | memory_retrieval    | 1.000 | 40  |
| 480 | recency_truncation  | 0.025 | 0   |
| 800 | context_packing     | 0.375 | 300 |
| 800 | memory_retrieval    | 1.000 | 40  |
| 800 | recency_truncation  | 0.025 | 0   |

Context packing is genuinely strong while the raw history fits inside its scoring cap. It isn't a
strawman. It only degrades once the conversation outgrows what a single scoring pass can see.
Memory retrieval holds perfect recall throughout with flat, bounded cost, and here that recall is
earned: the store is ~434 tokens against a 120-token budget, so at most 12 of the 40 facts fit and
ranking decides which. Full table and charts are in the notebook.

## Two bugs that were fixed, and why they matter to anyone building the same harness

Both of these silently inflated results, and neither announces itself. If you build something like
this, check for both.

**The memory store must be bigger than the token budget.** An earlier version used 10 facts
totalling 113 tokens against a 120-token budget. The whole store fit, so `approach_memory_retrieval`
packed all of it every time and the ranking step never decided anything. Its perfect recall was a
property of the budget, not the retrieval; a deliberately nonsensical query still scored 10/10.
Now there are 40 facts (~434 tokens), at most 12 fit, and a nonsense query returns a partial,
arbitrary slice. Check your store's token count against your budget before believing any retrieval
number.

**Hit detection must match the retrieved unit, not a substring.** An earlier version scored a hit
as `expected_snippet in assembled_text`. But `"IST"` is a substring of `"list"`, and both `"list"`
and `"Python"` appear in the filler pool, so two of the facts could register a hit off a filler
turn with nothing retrieved at all. That inflated recency truncation (a reported 0.20 where the
true value was 0.00) and context packing's tail (0.70/0.40 where the truth was 0.60/0.30). Hits
now require the fact-bearing turn itself.

## Known simplifications (read before citing the numbers)

**1. The extractor is a perfect oracle.**
`extract_memory_store()` in `src/sim.py` pulls out exactly the turns tagged as fact-bearing at
conversation-generation time. A real memory-writing pipeline (usually an LLM call deciding what's
worth remembering) is lossy: it will miss things, misfile things, or record something slightly
wrong. The main comparison isolates the retrieval and scaling question only.

`src/eval_lossy_extraction.py` puts a number on what that costs, by dropping a share of facts
before they reach the store. Memory retrieval's recall collapses to roughly its extraction
quality, flat across every conversation length, because a dropped fact is absent rather than hard
to find. Context packing has no extraction step, so the two are not penalised symmetrically: at
60% extraction, memory retrieval loses at 480 turns and only wins at 800.

**2. The default queries share vocabulary with the facts they ask about.**
See the table under "Two rungs of relevance scoring". This is why TF-IDF scores a perfect 1.0
on them, and why swapping in real embeddings appears to change nothing until you switch to
`PARAPHRASED_QUERIES`.
